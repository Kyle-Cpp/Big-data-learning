## 真实格式与数据口径

`PlayerGoalProfileJob.ProfileReducer` 的 key 是 `season|teamId|playerId`，后面的18列 value 为：

```text
season teamId playerId competition teamName playerName position
appearances starts minutes shots goals xg xg90 shrunkXg90
expectedMinutes lambda goalProbability
```

支持带 key 的19列和不带 key 的18列。赛季 `2005/2006` 统一为 `2005-06`。格式、ID、非有限数、负数、越界预计分钟或概率非法时返回 HTTP400，避免错误导入覆盖已有数据；相同自然键重复导入也会拒绝。

`minutes` 是该画像覆盖比赛的累计出场分钟；`expectedMinutes` 是一次预计出场的分钟，不能跨赛季相加。保留原始：

```text
lambda = shrunkXg90 * expectedMinutes / 90
goalProbability = 1 - exp(-lambda)
```

各赛季 StatsBomb 比赛覆盖不同。页面列出的进球、xG、分钟是已采集样本的统计，不保证包含完整赛季。球员概率是画像对应的估计，不能当成已经验证的未来比赛结果。

## 在其他电脑升级

新数据库直接使用更新后的 schema 创建表。

已经使用旧版数据库时：

1. 停止旧后端，换入本次源码。
2. 在仓库根目录执行迁移。需要 Python3 和 mysql 命令行；可交互输入密码，不把密码写进命令。

```bash
python scripts/migrate_player_profiles.py --host 127.0.0.1 --port 3306 --user root --database footpred
```

也可读取自己的私密配置：

```bash
python scripts/migrate_player_profiles.py --config application-local.properties
```

脚本先备份到 `player_profile_pre_season_v1`，补 season、team_id 并替换唯一键。支持重复执行。旧聚合行的赛季和球队 ID 不能从数据库逆推，迁移后暂为 NULL，必须重导入原始 MR 结果。备份表用于审计，不作为当前业务数据。

3. 重建前端资源与后端 JAR，再启动。Windows 使用对应的 node/npm、mvn 命令。

```bash
cd frontend
npm run build
cd ../backend
mvn package
# 按本机的配置文件启动生成的 JAR
```

4. 每个受影响的 run 都重导入自己的原始 players.tsv。新增接口只替换该 run 的球员结果，不影响其他模块。

```bash
curl -X POST http://127.0.0.1:8080/api/admin/import/players/local-mysql-20261030 \
  -H 'Content-Type: application/json' \
  -d '{"location":"runs/m3-092841/module3/players.tsv"}'
```

上述 location 相对于 `footpred.local.root`。换电脑时按实际导出目录调整，不能只运行 ALTER TABLE 就认为历史聚合数据已修好。

```sql
SELECT COUNT(*) FROM player_profile WHERE run_id='local-mysql-20261030';
-- 本次完整结果：10992
SELECT COUNT(*) FROM player_profile
WHERE run_id='local-mysql-20261030'
  AND (season IS NULL OR team_id IS NULL OR expected_minutes>90
       OR ABS(goal_probability-(1-EXP(-lambda)))>0.000002);
-- 应为0
```
